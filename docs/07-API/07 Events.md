# Purpose

This document defines the Event-Driven Architecture (EDA) used throughout the Project & Asset Management Platform.

Events enable loose coupling between modules, improve scalability, support asynchronous processing, and provide a foundation for automation, AI workflows, notifications, integrations, auditing, and real-time updates.

The objectives are to:

- Decouple business modules
- Enable asynchronous processing
- Support AI automation
- Improve scalability
- Simplify integrations
- Reduce module dependencies
- Enable future microservice migration

# Correlation ID

Every business transaction generates one Correlation ID.

Example

```text
Create Project

↓

Create Batch

↓

Assign Tasks

↓

Generate Notification

↓

Send Email

↓

Same Correlation ID
```

Used for tracing distributed operations.

---

# Event Bus

The platform abstracts event publishing behind an Event Bus.

Responsibilities

- Publish Events
- Subscribe Events
- Route Events
- Retry Failed Processing
- Logging
- Monitoring

---

# Event Publishing

Events are published only after successful business transactions.

Example

```text
Save Project

↓

Commit Transaction

↓

Publish ProjectCreated
```

Never publish events before data is committed.

---

# Event Subscription

Modules subscribe only to events they require.

Example

```text
ProjectCreated

↓

Notification Module

↓

Audit Module

↓

Search Module

↓

Reporting Module
```

Modules remain loosely coupled.

---

# Synchronous vs Asynchronous

### Synchronous

Use when

- Immediate response required
- Validation
- Authorization

---

### Asynchronous

Use for

- Notifications
- Emails
- Reporting
- AI Processing
- Search Indexing
- Webhooks

---

# Event Persistence

Events are not business records.

Persistent storage is optional.

Recommended approach

```text
Business Database

↓

Event Bus

↓

Optional Event Store
```

Future versions may implement full Event Sourcing.

---

# Event Ordering

Ordering is guaranteed only within a single transaction.

Consumers should not assume ordering across independent transactions.

---

# Idempotency

Consumers must process events safely.

If the same event arrives twice

↓

Ignore Duplicate

EventId is used for deduplication.

---

# Event Versioning

Every event includes

```text
Version
```

Example


# Event Security

Events should never contain

- Passwords
- Tokens
- Secrets
- Sensitive Financial Information
- Personally Identifiable Information unless required

Use identifiers instead of sensitive values whenever possible.

---

# Tenant Isolation

Every event belongs to one tenant.

Consumers must validate TenantId before processing.

Cross-tenant event processing is prohibited.

# Development Guidelines

Developers should

- Publish events after successful transactions
- Keep payloads small
- Use immutable events
- Avoid direct module calls when events are appropriate
- Ensure event handlers are idempotent
- Keep handlers focused on a single responsibility

---

# AI Development Guidelines

AI-generated event code must

- Use immutable event objects
- Publish events only after transaction commit
- Include correlation IDs
- Include tenant context
- Support retries
- Log processing failures
- Avoid business logic duplication

AI must never

- Publish events before persistence
- Modify event payloads after publication
- Depend on processing order
- Ignore duplicate event handling

# Summary

The Project & Asset Management Platform adopts an event-driven architecture centered on immutable, versioned business events. Events are published after successful transactions and consumed asynchronously by independent modules such as Notifications, Workflows, AI Services, Reporting, Search, SignalR, and external integrations. This architecture minimizes coupling, improves scalability, simplifies future microservice adoption, and provides a robust foundation for enterprise automation and real-time processing.
